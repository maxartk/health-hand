# Loop engineering для Health Hand

## Ідея

Health Hand не треба розвивати як набір разових задач типу “додай кнопку”, “пофікси форму”, “прикрути AI”. Його треба вести як систему циклів зворотного зв’язку:

```text
ціль → зміна → перевірка → сигнал → рішення → наступна зміна
```

Код стає дешевшим. Дорожчим стає правильний сигнал: чи клієнт реально записався, чи адміністратору зручно, чи автоматизація не створила хаос, чи сайт викликає довіру.

---

## 1. Agentic coding loop — технічний цикл агента

### Ціль

Агент може самостійно робити дрібні покращення Health Hand, але тільки якщо кожна зміна має автоматичну перевірку.

### Що має входити в цикл

```text
spec → code → local run → API checks → browser check → security check → report
```

### Для Health Hand це означає

Кожна зміна в сайті/порталі/API має проходити мінімальний набір перевірок:

- `python3 -m py_compile portal_api.py`
- `node --check app.js`
- local test DB, не production DB
- smoke check endpoints:
  - `/api/portal/health`
  - `/api/v2/services`
  - `/api/v2/availability`
  - `/api/admin/v2/catalog`
- browser check через Chromium:
  - landing відкривається;
  - форма запису бачить реальні послуги;
  - час показується тільки з доступних слотів;
  - portal route `/portal/` відкривається окремо;
- security check public web root:
  - `/portal_api.py` не доступний публічно;
  - `/portal.db` не доступний публічно;
  - `/migrations/...` не доступні публічно;
  - source/backup файли не доступні публічно.

### Definition of done для агента

Зміна не готова, поки агент не приніс реальний результат перевірки, а не просто “я зробив”.

## 2. Developer feedback loop — цикл Максима / власника

### Ціль

Людина не має бути QA для дрібних багів. Її роль — давати продуктовий сигнал.

### Не так

```text
“Тут кнопка не працює, виправ.”
```

Це агент має ловити сам через browser/API тести.

### Правильно

```text
“Цей запис незручний для клієнта.”
“Тут не зрозуміло, чому треба залишати контакт.”
“Адміністратору незручно підтверджувати час.”
“AI-асистент звучить не як салон, а як бот.”
```

### Для Health Hand цей цикл має питати

- Чи клієнт за 30–60 секунд розуміє, яку послугу обрати?
- Чи форма запису не відлякує?
- Чи після заявки клієнт розуміє, що буде далі?
- Чи адміністратор бачить достатньо даних для підтвердження?
- Чи портал справді корисний, а не просто “кабінет для галочки”?
- Чи AI-асистент не вигадує ціни, адресу, часи, контакти?

### Артефакт циклу

Після кожної ітерації має бути короткий changelog у форматі:

```text
Що змінили:
Що перевірили:
Що стало краще для клієнта:
Що лишається незрозумілим:
Наступний продуктовий ризик:
```

## 3. External feedback loop — цикл реальних користувачів

### Ціль

Не будувати “ідеальний CRM в пустоту”. Спочатку зібрати реальні сигнали з клієнтів і адміністратора.

### Події, які треба міряти

На landing:

- відкрив сайт;
- натиснув “Записатися”;
- відкрив форму;
- обрав послугу;
- обрав дату;
- обрав слот;
- відправив заявку;
- отримав підтвердження.

В адмінці:

- нова заявка переглянута;
- заявка підтверджена;
- заявка скасована;
- клієнт не прийшов;
- відправлено follow-up;
- клієнт записався повторно.

В AI-асистенті:

- скільки питань було про послуги;
- скільки питань було off-topic;
- скільки разів асистент привів до форми;
- скільки разів асистент не знав відповідь і правильно не вигадав.

### Основні метрики

- booking conversion: `submitted_booking / form_opened`
- slot selection conversion: `slot_selected / date_selected`
- confirmation rate: `confirmed / submitted_booking`
- no-show rate: `no_show / confirmed`
- repeat booking rate: `repeat_booking / completed_visit`
- admin response time: час від заявки до першого статусу
- AI containment rate: скільки off-topic запитів не пішли в модель або отримали fixed safe response

## 4. Практична loop-архітектура для Health Hand

### Щоденний/післязмінний tech loop

Запускається після кожної зміни коду:

```text
1. syntax checks
2. local API smoke tests
3. browser smoke test
4. screenshot
5. sensitive URL check
6. short report
```

Це зона AI-агента.

### Щотижневий product loop

Раз на тиждень дивимося:

```text
1. скільки людей зайшло
2. скільки відкрили форму
3. скільки обрали послугу/дату/слот
4. де відвалились
5. які заявки стали реальними записами
6. що адміністратор робив вручну
```

Це зона власника + агента.

### Щомісячний strategy loop

Раз на місяць вирішуємо:

```text
1. які послуги реально продаються
2. які тексти/фото викликають довіру
3. чи потрібен портал клієнтам
4. чи AI-асистент окупає себе
5. що прибрати, а не додати
```

Це вже продуктове рішення, не кодинг.

## 5. Найближчий правильний цикл для поточного стану

Поточний стан: v2 API для services/availability вже є, landing form уже підключена до реальних послуг і слотів у staging.

Наступний цикл має бути не “додати ще фіч”, а закрити feedback architecture:

### Крок 1 — технічний watchdog

Зробити одну команду/скрипт:

```text
health-hand-smoke
```

Він перевіряє локально або на staging:

- API health;
- services count > 0;
- availability returns slots for known service/date;
- landing contains booking form;
- app.js syntax OK;
- portal loads;
- sensitive files are not publicly exposed.

### Крок 2 — booking funnel events

Додати server-side або lightweight client-side події:

- `form_opened`
- `service_selected`
- `date_selected`
- `slot_selected`
- `booking_submitted`

Без Google Analytics, якщо не потрібно. Можна почати з SQLite table `events`.

### Крок 3 — admin feedback field

В адмінці для кожної заявки додати коротке поле:

```text
Чому клієнт підтвердився / не підтвердився?
```

Це дасть реальний продуктовий сигнал, а не фантазії агента.

### Крок 4 — weekly loop report

Автоматично генерувати раз на тиждень короткий звіт:

```text
- скільки заявок
- які послуги обирали
- які дати/часи популярні
- де люди відвалювались
- які заявки не підтвердилися і чому
- 3 рекомендації що змінити наступного тижня
```

## 6. Роль інженера в цьому проєкті

Для Health Hand інженер має бути не просто тим, хто “робить сайт”. Його роль:

- будувати технічні цикли, де агент сам ловить поломки;
- будувати продуктові цикли, де видно реальну поведінку клієнтів;
- будувати безпечні межі для AI-асистента;
- не додавати CRM-фічі без сигналу з реального використання;
- перетворювати кожну зміну в перевірювану гіпотезу.

Коротко:

> Health Hand треба розвивати не як сайт, а як систему вимірюваних циклів: запис → підтвердження → візит → повторний запис → покращення сервісу.
